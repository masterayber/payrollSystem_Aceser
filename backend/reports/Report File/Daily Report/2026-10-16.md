## What changed

### App and server split (PR #15)
- **`backend/app.js`** builds the Express app: body parsing, CORS, the seven `/api/*` route mounts, `GET /`, the `/api/protected` example and the `/uploads` static folder. It exports the app and doesn't connect, listen or schedule anything.
- **`backend/server.js`** now handles startup only, in this order: load `.env`, the `JWT_SECRET` guard, require `./app`, the HTTP server, Socket.IO, the MongoDB connection, the attendance scheduler, then `listen`.
- **Small corrections along the way:**
  - `.env` now loads before any route file.
  - The Socket.IO CORS option `method` (ignored) is corrected to `methods`.
  - The `useNewUrlParser`/`useUnifiedTopology` options, which do nothing in Mongoose 8, are gone.
  - `/api/protected` and `/uploads` are now registered before `listen`.
- **Verified by hand:**
  - The server starts with the real `.env`.
  - The guard rejects a short secret and a placeholder secret.
  - Admin and employee pages load, and profile photos still show.

### Backend tests (PR #15)
- **Dev dependencies:** `jest`, `supertest` and `mongodb-memory-server`, plus a `"test": "jest"` script.
- **Jest config in the root `package.json`:**
  - Node environment.
  - Only `backend/` is searched for tests.
  - A 30-second timeout, for starting the in-memory MongoDB.
  - `backend/tests/setupEnv.js`, which sets a test-only `JWT_SECRET` so tests never depend on a developer's `.env`.
- **`backend/tests/app.test.js`** starts a fresh in-memory MongoDB for the suite and clears data between tests. The first 8 tests:
  - `GET /` returns 200.
  - Login: the right password returns a token and no password hash; a wrong password returns 400; a pending account returns 403.
  - Admin-only guard on `GET /api/employee/employees`: no token returns 401, a forged token 401, an employee 403 and an admin 200.
- **`behavior.js` is now CommonJS.** It used `export`, but the backend loads it with `require()`. Node 22 tolerates that, so the server ran, but Jest doesn't. `summary.js`, `time.js` and `weeklySummary.js` stay as ES modules: the frontend `Dashboard.jsx` imports two of them directly, and the backend doesn't use any of the three.
- **CI:** a "Backend tests" step runs `npm test` at the end of the `check` job. CI doesn't need a `JWT_SECRET` secret, because `setupEnv.js` provides one and the tests never load `server.js`.

### Route audit and security fixes (PRs #17 and #18)
- **The Day 3 wiring list is fully resolved:**
  - `/api/settings` is mounted.
  - The dropdown, settings and filing-admin routes are guarded.
  - `MONGO_URI` comes from `.env`.
  - The settings guard reads `req.params.id`, and the guards run before `multer`.
  - The biometric scheduler stays disabled on purpose.
  - Every route is guarded except the intended public ones: login, signup, forgot password, OTP, reset password, and the signup-flow employee routes.
- **Critical: the OTP was in the forgot-password response** (`POST /api/auth/forgot-password`).
  - The risk: anyone who knew an email address, including the admin's, could read the code from the response and reset that password.
  - The fix: the OTP is no longer in the response, which now carries only the message and the expiry time. The frontend never read the OTP, so nothing broke.
  - The OTP now comes from `crypto.randomInt(100000, 1000000)`, which is always 6 digits and cryptographically secure. The old `Math.random()` formula sometimes produced 5 digits.
- **Critical: role escalation through the settings route** (`PUT /api/settings/updateGeneralSettings/:id`).
  - The risk: the route copied the whole request body onto the login record, so an employee could send `"role": "Admin"`. A `password` field would have been saved unhashed, locking the account. The response also included the password hash.
  - The fix: only `email` is accepted for the login record, since it's the only user-level field the settings pages edit. Validators now run, and the response leaves out the password.
  - The employee record is now found by `userId` instead of email. The email lookup used the new address, so it silently failed whenever someone changed their email. All 5 local employee records have a `userId`.
- **The regression from PR #17, fixed in PR #18.** While retyping the route, the employee update ended up writing `settings` instead of `employee`, so profile edits (name, address, emergency contact) stopped saving. The tests missed it because they always sent `employee: {}`. PR #18 restores `{ $set: employee }` and adds a test that creates an employee record and checks the saved contact number and city.
- **New tests (5, for 13 in total):**
  - Forgot-password doesn't return the OTP; nodemailer is mocked so no email is sent.
  - The settings route ignores `role`, `status` and `password` sent by an employee, and the old password still logs in.
  - An employee can still change their own email.
  - An employee gets 403 when editing someone else.
  - The employee's profile fields are saved.
